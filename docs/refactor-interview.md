# 最大困难：让功能堆积的 AI 世界重新围绕角色自主生活运转

## 约一分钟的面试回答

我遇到的最大困难，是项目功能逐渐增多以后，技术上的功能完整和实际的角色生活体验发生了偏离。旧版本已经有自主目标、日程、记忆和会话，但同时还存在导演事件、事件唤醒队列、体力生命、物品规则，以及 Python 的世界镜像。读代码和排查一次行为时，需要跨越很多模块，演示也容易变成查看工具执行记录。

我重新把目标限定为四个角色在小镇中工作、休息和交流，保留 Spring Boot、Python/LangGraph、React 等技术架构，但删除与这个目标无关的机制，并重新划分三件事：程序决定谁获得思考机会，模型选择行动，Java 校验和执行事实。

具体实现上，我把活动变成有开始和结束时间的持续状态，把对话变成需要邀请、接受和轮流发言的会话；把分散的记忆合并成带事件来源的记忆流，并将行动和角色认知在 Java 中一次提交保存。前端也围绕真实事件展示角色动机和计划。

验证时除了构建和关键规则检查，我使用原有模型跑了十轮，看到许宁主动邀请苏晚、苏晚中断读书接受邀请，随后双方交流。这个结果说明小规模闭环已经跑通，但我没有把短期试跑说成长期叙事质量或生产级并发能力。

## 怎么理解这次困难

不要简单说“旧系统没有自主性，所以重写”。旧系统已经有目标、Agenda（日程安排）和持续会话。真正的问题是：功能增加以后，核心体验不够集中，状态与调度链路太分散，理解、验证和演示一个角色行为的成本变高。

也不要把“删了很多行代码”当成解决效果。删除旧代码只是手段，主要结果是角色行为能通过一条清晰的链路解释，且前端所展示的事实确实经过 Java 结算。

## 三个关键决策

先记住这次实际改了什么：

| 处理 | 改动 | 目的与代价 |
|---|---|---|
| 保留 | Java/Spring Boot、Python/LangGraph、React、MySQL、Chroma、MCP、SSE、Skill | 保留技术架构，重建业务闭环 |
| 删除 | Director和作者专用环境干预接口 | 角色目标驱动；失去自动制造剧情的兜底 |
| 删除 | 体力生命、战斗追逐、完整物品操作和经济扩展 | 聚焦生活交流；不再是完整RPG模拟 |
| 重写 | 活动与邀请会话 | 持续活动、自愿回应、明确轮次 |
| 合并 | 多种分散记忆模块 | 保留亲历、听说、反思及来源，减少重复状态 |
| 收敛 | Python世界镜像与复杂事件反应调度 | Java权威状态；简化机会分配，便于追踪 |
| 增加 | Redis文本向量缓存 | 减少重复向量请求；不缓存角色决策 |
| 重写 | 前端群像记录和人物手记 | 能观察活动、短动机、计划和记忆 |
| 清理 | 失效测试、过期文档和旧运行模块 | 不维护两套语义；旧存档仅保留导出 |

### 1. 明确模型与世界规则的边界

模型负责目标、意图、计划、行动提议和简短动机。模型输出“我想找苏晚聊聊”，不等于世界里已经发生了交谈。

Java 检查双方是否同地点、是否存在其他会话、是否轮到本人发言等条件。通过以后才生成事件并保存。模型可以说出不真实的内容；系统只保证“某人说了这句话”是真实事件，不保证这句话的内容是真的。

代码：`agent/graph.py` 的 `decide`、`act` → `tools/remote_world.py` 的 `commit` → `WorldMcpTools.commitTurn` → `WorldRules.apply`。

### 2. 用明确的活动与会话状态代替复杂的反应链

每轮推进共同世界时间5分钟，Java完成所有到期活动，再由Python给最多两名不同NPC一次决策机会。活动可以同时持续，但模型调用是顺序执行，不是四个角色并行请求模型。

调度器参考活动、邀请、会话的发言人、个人计划和距离上次决策的时间。它负责机会分配，不指定剧情。删除Director后，系统没有自动注入冲突的兜底，角色可能安静读书或拒绝交流。

邀请也有自己的状态：发出邀请不代表对方同意。收到邀请的角色可以在忙碌时获得回应机会，接受后Java才中断活动并创建会话。会话只允许 `next_speaker` 发言；当前是双人会话，最多12条消息，45分钟无回应结束。

代码：`agent/tick.py` 的 `opportunities`、`WorldSession.next_tick`；`WorldRules.advance`、`WorldRules.apply`。

### 3. 把事实、认知与展示串成一次可追踪的提交

记忆统一为亲历、听说和反思，并保存源事件ID。Python观察事件时按 `perceived_by`（知情者名单）过滤；检索长期记忆时Chroma按owner过滤；世界设定按audience过滤。上帝视角可以展示全局信息，但NPC Prompt不直接接收全局视图。

Java在一次角色提交里校验行动、认知字段和记忆来源，生成真实事件，关联动机记录，随后用一次MySQL更新保存。MySQL通过revision（快照版本号）条件更新，避免旧快照覆盖新状态。这里采用整份JSON快照，不是复杂的分布式事务系统。

代码：`memory/stream.py`、`retrieval/chroma_index.py`、`characters/prompt.py`、`WorldMcpTools.commitTurn`、`WorldStore.update`。

## 一次真实行动：许宁邀请苏晚

1. React点击推进时间，Spring Boot转给本机Python控制服务。
2. `WorldSession.next_tick` 经MCP调用Java推进5分钟，许宁的等待活动到期。
3. 调度器给许宁一次思考机会，不规定他必须交谈。
4. LangGraph观察现场、检索许宁自己的记忆，加载适用Skill。
5. 模型提议 `invite`，目标是苏晚，输出邀请内容、简短动机和个人计划。
6. Python经MCP提交，Java确认双方同地点、许宁可以发邀请，保存邀请和真实事件。
7. 调度器重新计算候选人，苏晚因为收到邀请获得回应机会，尽管她仍在读书。
8. 苏晚模型选择接受；Java停止她的读书活动，移除邀请，创建会话。
9. 后续轮次按 `next_speaker` 分配发言，Java保存双方的话，SSE让React更新记录。

这段情节来自实际试跑，前端显示的动机是模型返回的简短解释，不是暴露模型内部完整推理，也不是Java确认的客观心理事实。

## 技术栈在当前版本中分别干什么

| 技术 | 当前职责 | 面试时不要误称 |
|---|---|---|
| React | 观察、人物手记、玩家交互 | 浏览器直接连接Python模型服务 |
| Spring Boot | 浏览器唯一入口、控制API、视图过滤、SSE、MCP工具 | 仅仅转发模型文本 |
| Python | 单机角色运行时和调度 | 第二份独立权威世界 |
| LangGraph | 观察→回忆→决策→提交→记录，格式或规则失败最多改选一次 | 训练出的独立大模型 |
| MCP | Python调用Java世界工具的协议入口 | 允许模型绕过Java改数据库 |
| MySQL | 权威快照、活动、会话、事件、认知与记忆 | 本项目已实现高并发数据库架构 |
| Chroma | 可重建的记忆和设定向量索引 | 权威记忆数据库或世界状态 |
| Redis | 文本向量缓存，键含模型、维度和文本摘要 | 任务队列、角色决策缓存 |
| SSE | Spring Boot向浏览器单向推送视图 | WebSocket双向通信 |
| Skill | 身份与情境相关的Markdown专业知识和策略 | 固定剧情脚本或必须执行的工具步骤 |

近期8条记忆直接进入Prompt；更早的记忆进入Chroma候选检索，再综合相关性、重要性和新近程度排序。反思积累至少5条新经历后可随一次决策生成，必须引用本人可见事件，不额外发起一次反思模型调用。

## 面试追问练习

**为什么Java和Python不合在一起？** Python便于组织模型和LangGraph，Java负责统一规则与持久化，MCP连接两者。代价是增加网络失败与状态同步问题，因此删除Python持久世界镜像，并给提交设置请求ID、给时间推进设置expectedTick。当前防重范围有限，不宣称无限期“恰好一次”执行。

**为什么不用Director避免无聊？** 项目要演示角色自身目标驱动的生活，所以删除外部剧情推进。自然交流通过角色目标、记忆、Skill和自愿邀请产生。代价是剧情质量不稳定，不能保证每段运行都有冲突。

**你是不是给角色写了脚本？** 活动目录和合法条件由程序定义；下一步行动、交谈内容和计划由模型选择。Skill提供知识和考虑因素，不规定固定调用顺序。程序仍然决定谁有机会思考，这是运行约束。

**怎么防止模型胡编？** 不允许模型文本直接改事实；Java白名单校验行动与参数，记忆引用校验本人可见事件。不能保证模型的所有主观印象或发言内容都真实，这些被明确标成认知或听说。

**为什么这次选择大改而不是继续补丁？** 功能已经偏离展示目标，继续追加兼容层会让状态链路更难读。保留技术架构，重新定义小范围业务闭环，删除无关模块；旧存档保留导出，采用新版本快照，明确不自动迁移。

**怎么证明有效？** Java和React构建、Python语法编译通过；临时离线闭环检查活动、会话、玩家隔离、SSE、保存恢复及规则拒绝。真实模型十轮产生21条事件并出现自主邀请和交流。没有新建大量测试，也没有长期质量、性能提升百分比或生产经验的数据。

## 当前局限与下一步

当前是小规模单机、单玩家、双人会话、顺序模型调用。JSON历史增长会增加读写成本，角色可能重复行为，叙事质量依赖模型。旧存档只能导出，没有自动迁移。

下一步应先观察较长运行中的重复行为和计划执行，再决定是否增加计划清理、记忆压缩或更好的调度。它们是未来方向，不能在面试里说成已经实现。
